# Worker

## Product contract

Worker is an independent internal portal, not a CRM integration.

- User-facing copy is native Spanish.
  Source code may remain English.
- CRM (`~/git/crm/apps/web`) is a visual and interaction reference only.
  Do not import its code, components, styles, data, or authorization model.
- Email/password authentication.
- Site administrators control users and teams.
- Team leaders alone submit and manage their own proxy configuration.
- Team members may search their team's published results.
- Results are fully visible within the authorized team and retained indefinitely.
- Ingest all stable sources already supported by the `fetch` package.
  Exclude the unstable browser source for now.
- Accept valid input rows and report exclusions.
- Teams own GeoNode or DataImpulse proxy credentials.
- Global execution limit: five jobs running or cancelling; excess work queues.
  Multiple worker processes are supported.
- Cancellation is immediate and preserves partial results.
- Notifications: in-app for the team, terminal email and Kapso WhatsApp according to the recipient policy still to be selected.

## Architecture

```text
Browser
  -> FastAPI routes
  -> Jinja page or HTMX fragment
  -> PostgreSQL application/repository transaction
  -> durable events and notification outbox

SSE endpoint
  <- durable PostgreSQL job events

Worker process
  -> authenticated /api/worker/claim
  -> stable fetch sources with the leased team's decrypted proxy configuration
  -> authenticated /api/worker/publish
  -> immutable result object reference + PostgreSQL publication/event
```

- `packages/portal/portal/web` is the FastAPI boundary: Jinja2, HTMX, SSE, session/CSRF and browser security.
- `portal/application` owns use cases and authorization.
- `portal/domain` owns states, source planning and queue policy.
- `portal/repository` owns PostgreSQL transactions, leases, fencing and queue control.
- `portal/worker` is an outbound worker client.
  It must not become a second queue or business-rule owner.
- `portal/storage` accepts immutable provider-neutral object references.
- `portal/integrations` is the notification adapter boundary.
- PostgreSQL is the queue control plane.
  Do not add Redis, Temporal, Trigger.dev, or another queue in this slice.

The central visual rule, derived from CRM, is one surface owner per functional region.
`Panel` owns the perimeter; forms, lists, tables, progress blocks and empty states do not add nested cards/borders/shadows.
Use the local token system in `portal/web/static/tokens.css` and local component CSS.

## Current implementation state

The branch already contains the following and must be extended in place:

- FastAPI/Jinja/HTMX pages with Spanish Worker terminology and CRM-derived local visual tokens.
- Email/password sessions, CSRF, trusted-origin/host protections, role checks and a site-admin boundary.
- First-team setup, email-based team/member administration, leader-only proxy configuration, encrypted credential handling and an explicit provision command.
- PostgreSQL migrations and a transactional five-active-job queue with leases, fencing, cancellation and durable job events/outbox rows.
- SSE response support and authenticated worker claim/publish endpoints.
- An outbound worker client in `portal/worker/service.py` that invokes stable fetch sources (`sunat`, `osiptel`, `sunat_reps`).
- Local immutable mounted-volume storage (`FileObjectStorage`), suitable for development but not the production object-store adapter.

Known gaps are intentional work, not reasons to rewrite the portal:

1. Complete and verify stable-fetch worker execution end to end against the current worker channel, including team-owned credential grants, retries/reaper behavior, fences, cancellation and partial publication.
2. Replace the development mounted-volume storage with the chosen production immutable object store.
3. Implement notification senders and retry/delivery bookkeeping for email and Kapso WhatsApp.
4. Add production deployment/cutover material: migrations, worker lifecycle, health/readiness, observability, backup/restore and security configuration.
5. Perform branch-history cleanup only after the production work is landed and reachability is proven.

## Next slice

Start here.

Goal: make the existing worker path a reliable stable-fetch execution path on the canonical branch.

- Begin with CodeGraph exploration of `portal.worker`, worker claim/publish routes, repository lease/publish methods, credential protection and source planning.
- Use only sources currently supported by the stable `fetch` package.
  Do not add browser automation or Entel/browser sources.
- Keep proxy credentials team-scoped.
  The worker receives only the grant needed for its leased item and must not log plaintext proxy credentials or secrets.
- Preserve sticky proxy execution for a leased job/source where the fetch adapter requires it.
- Validate worker registration/authentication, source allow-listing, claim lease expiry/reaper, bounded retry policy, fencing of late writes, cancellation and partial-result retention.
- Preserve the single PostgreSQL queue limit of five active jobs across worker processes.
- Keep worker-facing failures operationally useful but do not expose secret/configuration detail to browser users.
- Implement production behavior first; do not spend the slice expanding broad tests or redesigning the UI.
- Run focused validation once the implementation is complete, then update documentation only for real behavior.

Completion criteria:

- A provisioned leader can submit a valid batch without entering opaque IDs.
- A configured worker can claim work, run only stable sources through the fetch package and publish immutable per-item results.
- Team users can see live/terminal state and search published data under their existing authorization scope.
- Invalid rows are accounted for, source/item failures are visible, and cancellation retains published partial data.
- Multiple worker processes obey the global five-job cap.

## Captain decisions still needed

Before delivery/production work, choose:

1. Hosting and managed PostgreSQL provider.
2. Immutable object-store provider.
3. Transactional email provider.
4. Kapso recipient policy: submitter only, submitter plus opted-in team leaders, or another explicit role rule.

Recommended default: managed PostgreSQL plus S3-compatible object storage, an approved transactional email provider, in-app notification for all authorized team members, and terminal email/Kapso delivery to the submitting leader plus opted-in team leaders.

## Provisioning and local development

Use `mise`; do not require Docker for normal local development.

- `mise run install`
- Configure the root `.env` from `packages/portal/.env.example`.
- `mise run portal:dev` starts the repository-local PostgreSQL cluster when needed, migrates, provisions the local admin/first team, and starts the portal.
- `mise run portal:migrate` applies migrations.
- `mise run portal:bootstrap` performs idempotent local provisioning.
- The explicit provision command is `uv run --env-file packages/portal/.env python -m portal.provision ...`.
