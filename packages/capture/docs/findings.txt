ENTEL DEBT-BY-RUC LOOKUP PROCESS

Investigated 2026-07-17.

TARGET
- Site: https://miperfil.entel.pe/PE_Web_Cobro_Online_EU/ ("Paga tu deuda").
- Technology: OutSystems Reactive Web app.
- DataActions travel over XMLHttpRequest, not fetch. A window.fetch hook intercepts nothing.
- Probe host is in Peru (Cogent, 38.25.80.196). The reference browser (on the Windows host
  of the same WSL box) egresses from that same IP via WSL2 NAT. Mint-IP vs request-IP
  mismatch was therefore never a variable in any test in this file.

THE MECHANISM
- The app's own Step2 request must be blocked. Hooking XMLHttpRequest.prototype.send,
  capturing the Step2/DataActionGetData body, and returning without forwarding it holds the
  app on Step1. The loading spinner then hangs forever. That hang is the success state.
    Mints made while the page is still on Step1        -> ACCEPTED
    Mints made after the app reaches the Step2 screen  -> REJECTED
- With the block in place, an in-page fetch loop over grecaptcha.execute("0",
  {action:"SearchDebt"}) returns correct debt at ~0.8-1.4 s per RUC, with no decay across
  lookups, no cleanup between them, and no page reload per RUC.
- Removing only the block, in the same browser minutes later, yields 0/5. That is the
  strongest single-variable result on record here.

MEASUREMENTS
Real Chrome profile, hand-driven, 2026-07-17:
    6/6 correct (10:30), five distinct RUCs, ~1.2 s each
    5/5 correct (13:0x), 829-1382 ms each
    0/5 with the block removed, same browser, same hour
Real form drive, OS-level input, SeleniumBase UC browser, 2026-07-17:
    3/3 correct, one fresh browser per RUC, ~20 s per lookup
    4/4 correct, later in the same hour
    0/4 and later 0/9 the same afternoon, same script, same IP
Automated browser with the correct blocking recipe, 2026-07-17, every cell 0/5:
    throwaway UC profile | persistent user_data_dir (twice) | home IP | two fresh clean PE
    residential exits (America Movil 179.6.100.58, YOTTALAN 38.255.106.183) |
    explicit clear_cookies() (17 and 19 cookies cleared, page reloaded, form re-driven)

INPUT PRODUCTION
- Same SeleniumBase UC browser, same site, same form, same IP, only the input path differing:
    CDP-driven (sb.cdp.click / send_keys, isTrusted:true) -> HasErrorDebt:true
    OS-level (PyAutoGUI via a real X display)             -> real debt, 3/3 RUCs
- isTrusted is not sufficient. A CDP click reports isTrusted:true and is rejected anyway.
- An independent consumer agrees that CDP events are distinguishable: the OutSystems input
  mask also rejects CDP send_keys (only the first character lands) but accepts PyAutoGUI
  keystrokes cleanly.
- Hand-driven input in that same UC browser works. The browser build is not itself detected.

THE AUTOMATED BROWSER IS REJECTED WHERE A REAL CHROME PASSES (cause unknown)
- With the recipe that scores 5/5 by hand, the automated browser scores 0/5 across every
  cell in MEASUREMENTS above, while the user's ordinary Chrome on the same public IP
  returned real debt on demand at the same moment.
- The same UC browser passed 3/3 and 4/4 that morning and 0/4 that afternoon. It degraded
  during the day rather than being rejected by build.
- The tokens the automated browser sends are well-formed and fresh. Measured 2026-07-17
  with the block confirmed in place and the page confirmed held on Step1: length 1316-1358
  chars, a distinct token head per call (nothing cached or replayed), mint time 164-255 ms.
  Entel accepts none of them. The rejection is server-side on a valid fresh token.
- Not the variable, each tested directly: IP (two fresh clean PE exits fail identically; the
  working Chrome shares the probe host's public IP), cookies (clear_cookies plus reload
  changes nothing, and UC mode issues a fresh profile per run anyway), profile persistence
  (a reused user_data_dir fails twice), token freshness (above), the block (verified
  blocking in every failing run).
- What differs between the passing and failing case is unidentified. Every input to the
  request that can be controlled from this side has been matched to the passing run.
- The cliff (4/4 -> 0/4) followed bursts of rapidly minted rejected tokens. Those bursts came
  from probes missing the Step2 block, so they were minting tokens that could never pass.
  Whether a correct blocking loop degrades at all is UNMEASURED. A browser-level reputation
  surviving profile wipes, IP changes and cookie clears would fit the observations; so would
  other explanations. It is a hypothesis with no evidence separating it from the
  alternatives.

DEBT DATA ENDPOINT
- POST .../screenservices/PE_Web_Cobro_Online_CW/OnlinePayment/OnlinePayment_Step2/DataActionGetData
- Content-Type: application/json; charset=UTF-8
- Success: {"data":{"Debt":{"DocumentNumber":"<ruc>","DebtTotal":"<amt>","Accounts":{"List":[...]},
  "HasPunishment":bool},"HasErrorDebt":false,...}}
- Rejected: same shape with DocumentNumber:"", DebtTotal:"0.0", empty Accounts,
  HasErrorDebt:true, HTTP 200. This one shape is returned for every kind of rejection (bad
  token, spent token, expired token, empty RecaptchaId, dead session). It carries no
  diagnostic information.
- HasErrorDebt:false with DebtTotal "0.0" is genuinely no debt. The flag distinguishes, not
  the amount.

RECAPTCHA
- Site key: 6LdUZwUcAAAAAC_K3DlqC_WHKbDwXfYXZrV0Xrx5
- Action: "SearchDebt", confirmed live by hooking grecaptcha.execute rather than read from
  the bundle. Args observed: ["0", {"action":"SearchDebt"}].
- Widget id is the string "0", not the number 0. It matches RecaptchaId:"0".
- render=explicit; the app renders an invisible widget id 0 via reCAPTCHAReact.
- Tokens expire ~120 s. Single-use is ASSUMED from general reCAPTCHA behaviour and has not
  been measured against Entel.
- A token is consumed when Entel calls siteverify. A request rejected earlier in the pipeline
  (a CSRF 403, say) does not consume it.
- "Uncaught Error: reCAPTCHA has already been rendered in this element" is Entel's own
  double-render bug. Harmless, and not a lead.

CSRF
- HTTP 403 {"exception":{"message":"Invalid Login"}} means a missing or invalid anti-forgery
  token. It is not a captcha error.
- Bootstrap: GET app root -> GET moduleversioninfo -> POST GetData (403, Set-Cookie
  nr1Users/nr2Users) -> read crf from nr2Users -> resend with header X-CSRFToken.
- nr2Users is URL-encoded with %3d for '=' and %3b for ';'.
- The observed crf is the static anonymous string T6C+9iB49TLra4jEsMeSckDMNhQ= across
  sessions.
- Cookies osVisit/osVisitor/nr1Users are HttpOnly and unreachable from document.cookie. Only
  nr2Users is visible to JS. CDP reaches the rest.

TOKEN IS NOT PORTABLE TO httpx (one clean, controlled observation)
- Setup: block the app's Step2 XHR so the token is never spent at siteverify, capture the
  app's exact body plus that unspent token, replay from httpx with the full cookie jar taken
  via CDP.
- Result: httpx -> HasErrorDebt:true, while a normal in-browser lookup in the same session
  seconds later returned 726.91. Session and IP were healthy; the replay still failed.
- So "mint in a browser, call from httpx" does not work as-is. Something binds the token to
  the browser context. Whether that something is TLS is unresolved.

ENVIRONMENT
- Xvfb is sufficient. A PyAutoGUI-driven form on a headless virtual display returned real
  debt (20100000092 -> 726.91, err:false). XTEST input through Xvfb is not distinguishable
  by reCAPTCHA, which is what makes per-worker displays and horizontal fanout possible.
- On WSL, SeleniumBase's xvfb=True cannot work: WSLg mounts /tmp/.X11-unix read-only without
  the sticky bit, so no X server can bind a socket there, and chmod cannot change that. What
  works instead:
      Xvfb :99 -screen 0 1920x1080x24 -listen tcp -nolisten unix
      DISPLAY=127.0.0.1:99, plus an XAUTHORITY file that exists (touch one; WSLg's own
      socket needs no auth)
  -nolisten unix is the trick: the server never touches /tmp/.X11-unix. SB then runs with
  headed=True, not xvfb=True.
- On a normal server (zeus/poseidon) SB(uc=True, xvfb=True) should work. Known issue:
  activate_cdp_mode() spawns a second virtual display and does not pass xvfb_metrics through,
  so xvfb_metrics="1920,1080" silently yields 1366x768 and PyAutoGUI then throws "cannot
  click on point ... outside screen" (SeleniumBase discussion #3664).
- PyAutoGUI types into whatever window holds OS focus, so a shared display corrupts runs
  silently: a human typing elsewhere left an input holding "2" instead of a RUC, and another
  drive typed nothing at all. A dedicated display avoids this.
- SeleniumBase UC mode strips the proxy-auth extension, so an authenticated upstream proxy
  yields blank pages. A local no-auth relay that upstreams to the authenticated proxy and
  injects Proxy-Authorization works: entel_probes/relay.py, verified egress 179.6.100.58.

GOTCHAS IN THE FORM DRIVE (each cost a run)
- PyAutoGUI clicks screen coordinates, so anything below the fold needs
  scrollIntoView({block:"center"}) first (the dropdown options render at y~1157 on 1080p).

BENCHMARK AND COOKIE HYPOTHESIS - 2026-07-17 (15:20 UTC)
- A bounded sample input was prepared from seven RUC rows, including six distinct RUCs
  and one duplicate. The benchmark was intended to compare the installed system Chrome
  (/usr/bin/google-chrome, Chrome 149) with the extracted official Chrome stable binary
  (Chrome 150), using the direct CDP/PyAutoGUI runner and fresh named output artifacts.
- The system Chrome run did not reach page readiness. It emitted only the launcher
  diagnostic and produced no CSV results. This is a browser startup/headless failure,
  not an Entel HasErrorDebt rejection. The run was stopped without sudo.
- The extracted Chrome 150 runner had previously completed a full six-RUC-style session
  successfully. Its per-RUC wall times were approximately 1.6–1.7 seconds in the
  successful two-RUC control run, with reCAPTCHA mint times around 0.66–0.73 seconds
  and browser request timings around 0.42–0.53 seconds. The hand-driven reference
  remains approximately 0.8–1.4 seconds per RUC.
- The cookie explanation is currently not supported as the primary cause. Cookie
  clearing, fresh profiles, persistent profiles, and browser binary changes did not
  produce a stable acceptance boundary. The same relevant CSRF/cookie state appeared
  in both successful and later rejected sessions.
- Current interpretation: system Chrome still needs a separate startup investigation,
  while Entel acceptance remains intermittent after initialization. The leading
  unresolved boundary is server-side reCAPTCHA/token reputation or another opaque
  browser-session signal, not demonstrated cookie absence.
- Future benchmark protocol: use one persistent browser session, 10–20 distinct RUCs,
  no repeated health probes after rejection, and record per-lookup mint, request, total,
  and success fields. Avoid rapid exploratory token bursts because they may contaminate
  the acceptance signal.
- The document input is swapped when the document type changes:
  b9-b1-Input_DocumentNumber_Other becomes b9-b1-Input_DocumentNumber_DNI, holding a RUC.
  The id cannot be pinned; it has to be rediscovered.
- The dropdown swallows the first click while the app hydrates.
- Continuar is gated by both checkboxes and a complete RUC. A click on the disabled button is
  silently a no-op and produces no Step2 call, which looks exactly like a captcha rejection.
- Xlib needs an Xauthority file to exist.

THROUGHPUT
One browser running the in-page loop does roughly 3000/hour (~1.2 s/RUC, no reload, no
cleanup), against roughly 180/hour for the form-drive recipe (~20 s/lookup). At 1M-RUC scale
that is the difference between viable and not. Throughput is not the open question; holding
the session in an automated browser is.

OPEN QUESTIONS
- Why an automated browser is rejected while a real Chrome profile passes, same IP, same
  minute, same recipe, valid fresh tokens. Unidentified. This decides whether fanout is
  possible at all.
- Whether the blocking loop degrades within one session in an automated browser. Unmeasured;
  the hand-driven runs showed no decay across 6 rapid lookups, which is a small sample from
  one browser.
- The success rate of the blocking loop over many trials with RUCs rotated. Every number in
  this file is a handful of runs. Several past claims here were lucky windows reported as
  certainties.
- Whether the token binding is TLS. httpx with an unspent app-minted token fails while a
  same-session in-page control passes; curl_cffi with a real Chrome JA3/JA4 is untested
  (entel_probes/transports.py; first attempt inconclusive). Low value while the in-page loop
  is ~1.2 s/RUC.

REFUTED
- Cookie theory: real human session cookies plus a junk token still return HasErrorDebt:true.
  Entel's cookies carry session/CSRF identity only, no trust signal.
- _GRECAPTCHA reputation: it lives on recaptcha.net, is never sent to miperfil.entel.pe, and
  a real high-reputation browser's token still fails if minted programmatically.
- Session binding of the token: impossible in principle. siteverify returns only success,
  score, action and hostname, so Entel cannot correlate a token to osVisit.
- Pure-HTTP token minting via the recaptcha.net anchor+reload dance: rejected (no gesture).
  The reCAPTCHA release/version param A7KpaEASfhDcK0nXxgQEyyYv and base64 origin (co)
  aHR0cHM6Ly9taXBlcmZpbC5lbnRlbC5wZTo0NDM belong to this path and are recorded only for
  completeness.

THINGS WE THOUGHT BEFORE

Each was stated here as fact and each is refuted by an observation above.
- "The v3 score is below threshold for any automated/proxied/fresh-profile browser; only a
  high-reputation human browser passes." A stock UC-mode browser passes when driven by
  OS-level input.
- "The gate is the execution context of the mint; a trusted click makes the token
  acceptable." CDP clicks are trusted and fail. The claim generalized one true observation
  (inside a hand-driven browser, a console mint failed and a click mint worked) into a build
  spec it does not support.
- "The fast path is genuinely worse than the real form." The probes behind this verdict had
  silently lost the Step2 block, so they measured a broken script.
- "One IP degrades under sustained use, so rotating GeoNode PE exits is load-bearing."
  Refuted twice: two fresh clean Peru residential exits failed identically, and the reference
  Chrome kept working from the same public IP while automation failed.
- "TLS fingerprinting is a dead end." That came from a confounded test (a spent or
  console-minted token). It is unresolved, listed under OPEN QUESTIONS.
The common defect: the rejection response is identical for every failure mode, so a run
failing for reason A is indistinguishable from a run failing for reason B, and each of these
claims read a broken script or a lucky window as evidence about Entel. The readings that
resolved them all came from a human driving a real browser at the same moment, which is the
one control the automation cannot confound.
